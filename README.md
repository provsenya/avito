# Trip Service

HTTP-сервис для создания, получения и завершения поездок. Данные хранятся в
PostgreSQL, HTTP-контракт описан в OpenAPI.

## Требования

- Go версии из `go.mod`;
- `tripgoctl`;
- PostgreSQL и observability-стек из учебного окружения лабораторной 2.

Если `tripgoctl` установлен в `~/.local/bin`, добавьте каталог в `PATH`:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

## Запуск

Поднять учебное окружение и получить локальный `.env`:

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

Применить миграции и запустить сервис:

```bash
make migrate
make run
```

Проверить состояние миграций или откатить последнюю миграцию:

```bash
make migrate-status
make migrate-down
```

Перегенерировать HTTP-типы и серверный интерфейс после изменения OpenAPI:

```bash
make generate
```

`make generate` также генерирует gomock-моки из `contract.go`. Сгенерированные файлы коммитятся и вручную не редактируются.

| Переменная | Назначение | Пример |

| `HTTP_READ_HEADER_TIMEOUT` | таймаут чтения HTTP-заголовков | `2s` |
| `HTTP_WRITE_TIMEOUT` | таймаут записи HTTP-ответа | `10s` |
| `HTTP_IDLE_TIMEOUT` | таймаут keep-alive соединения | `60s` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | адрес коллектора из `.env` | `http://localhost:22318` |

Пример значений находится в `.env.example`. Локальный `.env` создаётся
`tripgoctl` и не коммитится.

## HTTP API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/trips` | создать поездку |
| `GET` | `/api/v1/trips/{tripId}` | получить поездку |
| `POST` | `/api/v1/trips/{tripId}/finish` | завершить поездку |
| `GET` | `/health` | проверить, что процесс работает |
| `GET` | `/ready` | проверить доступность PostgreSQL |

Ошибки бизнес-ручек возвращаются в формате `application/problem+json`.

## Решения

### Уровень изоляции транзакций

Используется стандартный для PostgreSQL уровень `READ COMMITTED`. Для создания
поездки согласованность обеспечивает уникальный частичный индекс, а для
завершения - условие `status = 'active'` непосредственно в атомарном `UPDATE`.
Более строгий уровень изоляции для этих операций не нужен и увеличил бы число
конфликтов транзакций.

### Менеджер транзакций

`TxManager.Do` открывает транзакцию и сохраняет `pgx.Tx` в `context.Context`.
Репозиторий выбирает исполнителя запроса из контекста: внутри `Do` это
транзакция, снаружи - `pgxpool.Pool`. Поэтому прикладной сервис не зависит от
`pgx` и не передаёт транзакцию параметром в каждый метод.

При успешном завершении функции выполняется `COMMIT`. При ошибке или панике
выполняется `ROLLBACK`; паника после этого пробрасывается дальше. Вложенный
вызов `Do` видит уже открытую транзакцию в контексте и переиспользует её.

Создание поездки и запись начального статуса выполняются в одном `Do`.
Завершение поездки и запись перехода `active → completed` также атомарны.
Начало транзакции, каждый SQL-запрос, commit и rollback ограничены
`DATABASE_QUERY_TIMEOUT`. Rollback использует отдельный контекст очистки,
который не отменяется вместе с запросом.

### Одна активная поездка на водителя

Ограничение реализовано частичным уникальным индексом
`trips_one_active_per_driver_idx` по `driver_id` для строк со статусом
`active`. PostgreSQL сохраняет правило и при конкурентных запросах. Ошибка
уникальности с кодом `23505` и именем этого индекса преобразуется в доменную
ошибку `driver_busy`, а HTTP-слой возвращает `409`.

### Конкурентное завершение

Usecase читает поездку через `SELECT ... FOR UPDATE` внутри транзакции и вызывает
доменный `Trip.Finish`. Второй конкурентный запрос ждёт блокировку и после
commit первого видит `completed`. Репозиторий дополнительно сохраняет условие
`status = 'active'` в `UPDATE`, поэтому повторное обновление не перезапишет время.

## Архитектура

```text
HTTP → usecase → domain/model
          ↑
     repository → infra/postgres

container → конкретные реализации всех зависимостей
```

- `cmd/trip-service` читает конфигурацию, создаёт контейнер и запускает сервис.
- `internal/container` — единственная точка сборки зависимостей и жизненного цикла.
- `internal/domain/trip` содержит статусы, переход `Finish`, валидацию и ошибки.
- `internal/model` задаёт типы, передаваемые между слоями, через алиасы доменных моделей.
- `internal/usecase/trip/{create,get,finish}` выполняет сценарии через интерфейсы.
- `internal/http/trip/{create,get,finish}` содержит HTTP-обработчики.
- `internal/http/domainerror` единожды переводит ошибки в `Problem`.
- `internal/repository/trip` выполняет параметризованные запросы через squirrel и pgx.
- `internal/infra` содержит пул, контекстный менеджер транзакций и телеметрию.

У каждого действия свой пакет. Неэкспортируемые интерфейсы находятся в
`contract.go` потребителя: он определяет нужные методы, а реализация зависит
от этого контракта. Моки лежат рядом с тестами. Правила импортов проверяет depguard.
OpenAPI-код оставлен в `api/`, как в первой лабораторной и общих соглашениях курса;
это позволяет сохранить существующую команду генерации и импорты контракта.

## Тесты и качество

```bash
make generate
make lint
make test
make test-integration
```

`make test` запускает unit-тесты с `-race -count=2` и печатает покрытие.
Домен и каждый usecase покрыты более чем на 50%. Тестируются переходы статусов,
валидация, доменные ошибки, обработчики и middleware с восстановлением паники.

`make test-integration` использует `DATABASE_URL` из локального `.env`, требует
запущенный PostgreSQL и запускает тесты с тегом `integration`, `-race -count=2`.
Каждый тест создаёт отдельную схему, применяет существующие миграции и удаляет
схему после завершения. Рабочие таблицы сервиса не затрагиваются. Проверяются
CRUD, конфликты, конкурентный finish, rollback обеих вставок при ошибке,
вложенные транзакции, rollback при панике и таймаут ожидания соединения.

## Телеметрия

Порядок middleware: `Recover → Tracing → Logging → Metrics → router`.
Маршрут предварительно сопоставляется через chi, поэтому имя спана и метрики
содержат шаблон `/api/v1/trips/{tripId}`, включая счётчик активных запросов.
Неизвестные маршруты получают фиксированное значение `unmatched`.

HTTP-спаны создаёт `otelhttp`. HTTP-метрики регистрируются отдельным middleware;
встроенные метрики `otelhttp` отключены, чтобы не считать запросы дважды.
DB-спаны создаёт `otelpgx` на уровне пула. Тонкая обёртка добавляет имя таблицы
и histogram `db.client.operation.duration` с обязательными атрибутами.
Автоматические prepare-спаны исключены режимом `QueryExecModeExec`, параметры
SQL в телеметрию не отправляются.

Usecase после успешного commit увеличивает бизнес-счётчик через интерфейс
и пишет бизнес-событие. JSON-логгер передаётся зависимостью, его handler добавляет
`trace_id` и `span_id` из контекста. Middleware пишет одну запись на запрос;
при панике в неё попадает стектрейс, клиент получает безопасный `500`.

Экспорт идёт асинхронно по OTLP, сэмплирование читает стандартный OTel SDK.
Недоступность коллектора не блокирует HTTP-запросы. Shutdown ждёт HTTP-запросы,
закрывает пул и сбрасывает телеметрию в общем бюджете `SHUTDOWN_TIMEOUT`.

URL интерфейсов показывает `tripgoctl connect`. В Grafana Explore выберите
Prometheus и выполните:

```promql
http_server_request_duration_seconds_count
tripgo_trips_created_total
tripgo_trips_completed_total
db_client_operation_duration_seconds_count
http_server_active_requests
```

Встроенный учебный dashboard может содержать метрики другого сервиса;
для проверки TripGo используйте Explore. Скриншоты и результаты проверки
для описания PR находятся в [docs/lab2-verification.md](docs/lab2).
